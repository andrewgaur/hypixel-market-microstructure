RANK 5 OF 8: A CLI AND REPRODUCIBLE ENVIRONMENT
============================================
Why fifth
---------
You need basic setup immediately. The fuller work belongs here because the
operations being exposed should first have stable meanings and tests. A clear
interface saves you from editing source code every time you change a horizon.

Concepts from the beginning
---------------------------
CLI means command-line interface: you ask a program to do something by typing a
command. An argument supplies a value; a flag selects an option. --help explains
the available settings. The working directory is where the shell currently is;
relative paths such as data/example.csv are interpreted relative to it unless
the program explicitly chooses another base.

A dependency is an external Python library. A virtual environment isolates a
project's dependencies from other projects. Pinning means recording exact
versions. Reproducibility additionally needs the input data, code version,
settings, and random seed. A seed makes a pseudorandom sequence repeatable;
it does not remove statistical uncertainty.

Step-by-step implementation
---------------------------
1. From a fresh checkout with the tested Python 3.14 interpreter, create an
   environment with python -m venv .venv-analysis2. This workspace already has
   one, so you need not recreate it to use the files delivered here.
2. Install the supplied analysis-specific dependency file:
   .\.venv-analysis2\Scripts\python.exe -m pip install -r requirements-analysis2.txt
   This does not install requests for the separate collector. Keep the existing
   requirements.txt available for its original purpose. The new lock records
   the versions actually installed for analysis2 testing.
3. Run --help, then the tests. Always use the environment's executable if your
   default python points somewhere else. "No module named pandas" commonly
   means you selected an interpreter where dependencies were never installed.
4. Run the default diagnostic command in 00_start_here_ranking.txt. Open the
   new output folder named in the console. Each run gets a new directory so
   yesterday's evidence is not replaced by today's experiment.
5. Learn one flag at a time: --input selects a CSV; --horizons 1 5 selects two
   forecast delays; --seed fixes resampling; --output names a new directory.
   Never use --book-sides-verified merely to silence an error. It records an
   assertion about prior verification of the input's economic quote semantics.
6. Read parser() in analysis2. argparse.add_argument defines an option, its
   type, and its default. main() rejects nonsensical combinations before work
   begins. Add settings only when their meaning and valid range are clear.
7. For a larger future CLI, expose collect, clean, validate, backtest, and report
   as subcommands. Start by having each call an existing tested function. Do
   not duplicate calculation logic inside the argument-parsing layer.
8. Move repeated study settings into a versioned TOML configuration file when
   commands get unwieldy. Decide which values take priority: explicit command
   arguments, then configuration, then defaults. Save the resolved settings
   rather than only the filename, since the file may change later.
9. Add a small installable package with pyproject.toml once modules stabilize.
   This file describes the project, its dependencies, and package location.
   Packaging lets python -m bazaar_ofi work consistently instead of depending
   on ad hoc import paths. It is a future improvement; analysis2 is a standalone
   script under src and does not require packaging to run today.
10. Record input hashes, script/code versions, interpreter/library versions,
    settings, and seeds in every run manifest. analysis2 already does this,
    including script hash and Git working-tree status. A dirty Git state means
    there were uncommitted changes, so the commit alone is insufficient provenance.
11. Give another clean environment a small frozen input and exact command. Check
    that sorted prediction values and metrics agree within a documented numeric
    tolerance. Byte-identical charts are not necessary; scientific values and
    their provenance are the important first reproducibility checks.

Small exercise
--------------
Run the same verified synthetic fixture twice with the same seed, each into a
different output directory. Compare numeric predictions and intervals. Then
change only the seed: predictions should stay fixed, while bootstrap interval
endpoints may move slightly. This separates model fitting from uncertainty
resampling in your understanding.

Current script connection
--------------------------
analysis2 has argparse, validated settings, import safety, a tested dependency
file, and per-run manifests. Full collector/clean/backtest subcommands and a
packaged application remain future work. Read the usage/fixes file for details.

Completion checkpoint
---------------------
You can reproduce a documented run without editing Python source, and someone
else can identify the exact code, input, environment, and configuration used.
