RANK 2 OF 8: RETRIES, BACKOFF, RATE LIMITS, LOGGING, MONITORING
===========================================================
Why second
----------
A month-long run needs to survive ordinary network failures. Reliability pays
off every day collection runs. Build basic recovery now, then add convenience
dashboards only when the simpler health information is useful.

Concepts from the beginning
---------------------------
A request can fail because your network is down, the service is busy, the reply
is malformed, or the service is limiting requests. An HTTP status is a number
describing the reply: 200 usually means success; 429 means throttling; selected
5xx statuses often indicate server trouble. A JSON success field is another
check, separate from HTTP status.

A timeout stops a request from waiting forever. A retry makes another attempt.
Backoff means waiting longer between failed attempts, rather than hammering a
busy server. Jitter adds randomness to waiting times. A rate limit is a request
budget imposed by the service. Logs describe events; monitoring checks whether
the recent events indicate a healthy process. A running process can still be
unhealthy if it keeps receiving stale data or fails to write to disk.

Step-by-step implementation
---------------------------
1. In the collector, extract fetch_once() from the while loop. Give it the URL
   and an HTTP session; have it return the response or a classified failure.
   A Session reuses connection machinery across requests. Keep parsing separate.
2. Put the loop inside main() and use if __name__ == "__main__": main(). This
   tells Python to start collection only when running the file directly, so
   importing the function in a test will not start an endless collection run.
3. Keep explicit connection and read timeouts. Check status before treating a
   body as valid market JSON. Handle 200 with success=false, malformed JSON,
   missing products, and missing tracked items with different logged reasons.
4. Start with a bounded retry loop: try at most five times, recording the attempt
   number. Retry transient connection errors and selected 502/503/504 responses.
   Avoid retrying invalid configuration or coding errors indefinitely. A five-
   attempt policy is a proposed starting setting, not an API requirement.
5. When no server wait is supplied, try a random delay up to min(60, 2**attempt)
   seconds. When Retry-After is supplied, respect its seconds or HTTP-date form.
   Do not cut a server-required wait to your own shorter cap. If it exceeds the
   current retry budget, postpone the next scheduled cycle too.
6. Check service documentation before increasing frequency. Do not assume public
   endpoints have the same key-based rate headers. Save available status and
   timing information, excluding credentials. Reference: https://api.hypixel.net/
7. Schedule using a monotonic clock, which measures elapsed time without jumping
   when the system clock changes. The old sleep(60) after work means each cycle
   lasts 60 seconds plus request/processing time. Calculate the next intended
   slot, and skip missed slots rather than making a burst of catch-up requests.
8. Replace important print statements with JSON Lines records. Each line should
   have time, severity, event, request_id, attempt, latency_ms, status, rows_saved,
   and error_type where relevant. For example:
   {"event":"fetch_failed","attempt":2,"status":429,"severity":"warning"}
   Consistent field names make counting failures straightforward.
9. Update a heartbeat file after successful durable writes. Include last fresh
   source time, last HTTP success, last write time, and consecutive failures.
   Write a temporary heartbeat and replace the old one only when complete.
10. Add an independent scheduled health checker. A crashed collector cannot
    tell you it has crashed. Start by producing a local unhealthy status if
    no durable write has occurred for five expected intervals. Review and tune
    this threshold during a pilot; stale source updates need a separate check.
11. Rotate logs and monitor free disk space. Allow only one collector instance
    to write the dataset. On Ctrl+C, close files cleanly. On restart, detect
    partial files and avoid duplicating already accepted source observations.

Small exercise
--------------
Before real collection, replace HTTP with a fake function returning timeout,
429, then success. Replace sleep with a function that records requested waits.
Verify the attempts and waits without waiting in real time. Also test five
failures: the program should reach a documented recovery/stop state.

Common mistake
--------------
"except Exception: continue" makes a loop look robust while hiding bugs forever.
Log unexpected exceptions with their traceback and distinguish them from known
temporary network failures. Counting successful requests also does not measure
unique market observations; a cached response may repeat the same source state.

Current script connection
--------------------------
analysis2 is an offline reader. It records run state and errors, but deliberately
does not fetch or retry HTTP. These steps apply to bz_data_collector.py and any
future storage module, not a setting in the analysis script.

Completion checkpoint
---------------------
You can simulate failures, explain exactly what happens, restart cleanly, and
tell from health records whether fresh usable data is actually being saved.
