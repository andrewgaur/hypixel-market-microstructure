RANK 1 OF 8: IMMUTABLE RAW DATA, CLEANED PARQUET, DOCUMENTED SCHEMA
================================================================
Why first
---------
Incorrectly reduced data cannot always be repaired. Saving the original response
lets you fix your interpretation later without losing weeks of observations.
Start with raw preservation and verified extraction; Parquet optimization can
wait until the collector is stable. This task has the highest dependency value.

Concepts from the beginning
---------------------------
An API is an interface that returns data when your program makes a request.
Hypixel returns JSON: structured text made of objects, lists, names, and values.
Python loads a JSON object into a dictionary, where you retrieve a value by its
key. A response is one returned message, potentially containing many items.

Your CSV is already processed: it keeps selected prices and sizes but loses
other levels and response metadata. Raw means preserving what arrived before
your selection logic. Immutable means you do not change a saved raw response;
you create a new cleaned version if your interpretation changes.

Think of raw data as the original photograph and cleaned data as the measurement
table you make from it. You can redo measurements if you retain the photograph.
Parquet is a table file format that stores column types and compresses well.
It does not make incorrect values correct. A schema is the written agreement
about what each column means, which values it permits, and its units.

Step-by-step implementation
---------------------------
1. Preserve data/bazaar_data.csv and note that its quote mapping is uncertain.
   Do not globally replace its prices. The collector takes max(buy_summary)
   and min(sell_summary); reversing those stored columns cannot recover an
   unrecorded minimum or maximum from the original arrays.
2. Save one new full response to a separate test file. Keep response.content
   bytes, receipt time in UTC, HTTP status, and a unique request ID. UTC is a
   common world time reference; a unique ID distinguishes separate requests.
3. Establish economic meanings. A bid is what an immediate seller receives;
   an ask is what an immediate buyer pays. Compare an API example to the same
   item's in-game quotes close in time. Identify the matching arrays and best
   levels. Record the evidence and a small fixture, not just your conclusion.
   Official endpoint reference: https://api.hypixel.net/
4. Write a function parse_snapshot(payload) that returns one row per tracked
   item. A function is a reusable named calculation. Keep fetching and writing
   outside this function so you can call it with a saved example in a test.
   Take the highest price on the verified bid side and the lowest on the
   verified ask side, and aggregate same-price sizes only as semantics require.
5. Create data/raw/date=YYYY-MM-DD/. Save each response using a UUID filename,
   first to a temporary file, then finalize only when writing completes. Never
   overwrite a finalized ID. A partial write must not look like a complete
   observation after a crash. Preserve failed-response bodies separately.
6. Keep a manifest: a list of files with IDs, timestamps, and SHA256 hashes.
   A hash is a compact fingerprint; if the bytes change, the fingerprint will
   almost certainly change. It detects modification but is not a backup.
   Finalize the response before recording it as durable in the manifest.
7. Write docs/data_schema.md. For each field record name, type, unit, whether
   it may be missing, and source. Initial fields: item_id (text), request_id
   (text), received_at_utc (timestamp), source_updated_at (timestamp if known),
   bid_price/ask_price (coins per item), bid_size/ask_size (item units), and
   quality_flags (list of reasons). State that (request_id,item_id) is unique.
8. Validate each row: finite positive prices, finite nonnegative sizes, a
   recognized item, an interpretable timestamp, and bid <= ask under the verified
   interpretation. A missing value means unknown; zero is an actual number.
   Keep rejected observations with reasons rather than erasing their existence.
9. Write a clean command that reads saved responses and creates a table without
   calling the network. Install PyArrow in the environment when implementing
   this step. Use an explicit Arrow schema and daily Parquet batches. A simple
   pandas prototype is df.to_parquet(path, engine="pyarrow", index=False).
   Read it back and check types, row counts, and several values. Reference:
   https://arrow.apache.org/docs/python/parquet.html
10. Repeated source lastUpdated values can reveal duplicate cached responses.
    Archive requests, but define how repeated source updates are excluded from
    analysis. Identical prices alone do not prove that a response was stale.
11. Rebuild a second cleaned directory from the same raw inputs. Compare sorted
    logical rows and rejection counts. If they differ, find why before scaling.
    Record parser/schema versions; never silently change an old dataset's meaning.

Small exercise
--------------
Use a synthetic bid list with prices 98, 99, 97 and an ask list with 102, 101,
103. You should extract bid 99 and ask 101: spread 2, midpoint 100. Test an empty
ask list next. The result should be flagged as incomplete, not ask price zero.

Current script connection
--------------------------
bz_ofi_analysis2.audit_rows rejects crossed/invalid quotes and writes reason
codes, but it cannot archive responses that the old collector never saved.
Its book-side verification flag records your prior verification; it performs
no API interpretation itself. Raw storage and Parquet remain work to implement.

Completion checkpoint
---------------------
